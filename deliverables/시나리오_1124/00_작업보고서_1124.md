## 1. 목적

가상의 3팀(마케팅·인사·개발) × 3직급(팀장·과장·사원) 조직을 만들고, 기존에 적재된 문서 187건으로 챗봇을 테스트합니다.
**직급과 팀에 따라 검색되는 문서와 보이는 개인정보가 실제로 달라지는지** 확인하는 것이 목적입니다.
소스 코드는 바꾸지 않고, 기존 기능과 DB 데이터만 사용했습니다.

## 2. 핵심 결론 (지금까지)

| 확인 항목 | 결과 |
|---|---|
| ③ 다른 팀 문서 차단 | ✅ 지원됨. 팀 밖 문서는 검색 전에 제외됨 |
| ② 같은 팀 안 직급별 문서 차이 | 🔶 일부. 시스템은 "팀 전체 / 본인 담당" 2가지뿐이라 **중요도 등급 기준 차단은 불가**. 담당자 배정으로 **사원 = 일반 문서만**은 구현했으나, **과장은 매우 중요 문서도 보임** |
| ① 직급별 개인정보 7종 열람 | ❌ 미지원. 설정은 "복원 허용 켜짐/꺼짐" 1개뿐이고, **실명 복원 기능 자체가 구현되어 있지 않음** (모든 직급이 이름표만 봄) |
| ④ 개인정보 원문 노출 | ⚠️ **탐지 누락 문서 16건** 발견 (가명처리되지 않은 이름 등). 권한과 관계없이 노출될 수 있음 |

## 3. 단계별 작업 내용

### 1단계. 현황 조사 (읽기 전용)

- **권한 구조**: 팀·직책별 검색 범위(`OWN` / `TEAM` / `NONE`) + 확정 문서만 검색. 다른 팀 문서는 볼 수 없음.
- **조직**: DB 팀 12개 (문서가 있는 팀 11개), 직원 35명. 마케팅(T01)·인사(T07)·개발(T10)에 팀장·과장·사원이 1명씩 이미 등록되어 있음.
- **개인정보 라벨**: 7종 모두 적재 문서에 있음 (이름 531, 전화 147, 주소 61, 주민번호 44, 이메일 43, 계좌 41, 카드 27개).
- **문제**: 세 팀 소속 문서는 56건뿐이고, 라벨도 팀마다 3종뿐이라 테스트 범위가 부족함.

### 2단계. 조직도와 계정 명단 → `01_조직도_계정명단.md`

- 사용자 결정으로 **11개 팀을 3팀으로 줄이고, 문서 187건을 업무 성격에 맞게 다시 배정**했습니다.
  - 마케팅팀 72건: 고객·영업 (상담·심사·분쟁)
  - 인사팀 56건: 인사·경영지원·재무
  - 개발팀 59건: IT·보안·시스템
- 새 팀·새 직원은 만들지 않았습니다. 기존 팀 코드와 사번을 그대로 썼습니다.

### 3단계. 개인정보 권한표 → `02_개인정보_권한표.md`

- 요청 정책: 팀장 7종, 과장 3종(이름·전화·계좌), 사원 1종(이름)
- 현재 시스템으로는 **라벨별 허용을 표현할 수 없고, 복원 기능도 없음**
- 예상 판정 (라벨 7종 × 직급 3개 = 21칸): **차단은 동작하고, 허용(실명 표시)은 "미지원"**
- 개선안을 따로 작성했습니다 → `개선안_라벨별_실명복원.md`
  - 정책에 라벨 목록 칸 추가, 복원 전용 읽기 계정, 서버에서 복원, 출력 재검사, 복원 기록
  - 백엔드 개발이 필요해서, 팀 합의 후 진행할 항목입니다

### 4단계. 문서 중요도 분류 → `03_문서_중요도_분류표.xlsx`

| 팀 | 일반 | 중요 | 매우 중요 | 검토 필요 |
|---|--:|--:|--:|--:|
| 마케팅팀 | 5 | 30 | 37 | 9 |
| 인사팀 | 14 | 19 | 23 | 7 |
| 개발팀 | 31 | 10 | 18 | 18 |

- **분류 기준**: 문서 유형의 업무 성격과, 본문에 들어 있는 개인정보 이름표 종류 중 **더 높은 쪽**
  - 일반: 개인정보 없음, 또는 직원 연락처만
  - 중요: 고객 이름·전화·이메일
  - 매우 중요: 주민번호·카드·주소·계좌
- **검토 필요 34건**: 탐지 누락 문서 16건, 연락처가 직원 것인지 거래처 것인지 판단이 어려운 문서 18건
- **서버를 고치지 않고 직급 권한을 맞추는 방법**: 담당자를 일반 → 사원, 중요 → 과장, 매우 중요 → 팀장으로 배정
  - 사원은 "본인 담당 문서만" 검색하므로, 결과적으로 일반 문서만 보게 됩니다

### 5단계. 시나리오와 질문지 → `04_시나리오_질문지.xlsx`

- 9개 계정 × 13문항 = **117건**
  - Q1~Q3: 일반·중요·매우 중요 문서
  - Q4~Q10: 개인정보 7종
  - Q11~Q12: 다른 팀 문서
  - Q13: 이름표 직접 입력
- **설계상 발견**: 질문에 이름표(`<PERSON_…>`)를 넣으면 개인정보로 탐지되지 않아 이름표로 문서를 찾지 못합니다.
  - 그래서 질문은 **날짜·번호·제목으로 대상 문서를 가리키는 방식**으로 만들었습니다.
- 예상 판정: 팀장은 미지원 22건, 과장은 정책 불일치 16건, 사원은 대부분 통과

### 6단계. DB 반영 (사용자 승인 후) → `05_6단계_DB변경목록.md`

| 변경 | 결과 |
|---|---|
| 변경 전 백업 | `backup_변경전_1124.csv` (개인정보·비밀번호 없음) |
| 문서 담당 팀·직원 변경 | 169건 |
| 마케팅팀 사원 검색 범위 `TEAM` → `OWN` | 1건 |
| 로그인 계정 발급 | 9개 (첫 로그인 때 비밀번호 변경) |
| 변경 이력 (`permission_change_log`) | 179건 |

- 한 트랜잭션으로 처리했고, 관리자 저장과 같은 검사를 거쳤습니다.
- 하지 않은 것: 팀 "사용 안 함" 처리, 문서 원문과 상태 변경
- **계정별 검색 가능 문서 수 (반영 후 DB에서 확인)**

| 팀 | 팀장 | 과장 | 사원 |
|---|--:|--:|--:|
| 마케팅 | 72 | 72 | 5 |
| 인사 | 56 | 56 | 14 |
| 개발 | 59 | 59 | 31 |

- **영향**: 예전 영업1·2팀 계정 8개(팀원 작업 4용)는 이제 문서 0건입니다.
  - 공유 폴더의 접속 안내 문서를 새 계정 기준으로 바꿨습니다.
- 계정별 안내 파일 9개를 만들었습니다 → `계정안내_개별/`
  - 비밀번호가 들어 있어 git에서 제외되도록 설정했습니다.

### 7단계. 챗봇 테스트 (진행 중)

- **방법**: 챗봇 서버와 같은 검색·답변 함수를 직접 호출하고, 계정별 허용 문서는 서버와 같은 규칙으로 계산합니다.
  - 로그인을 거치지 않으므로 **팀원용 임시 비밀번호는 바뀌지 않습니다.**
  - 답변에 원문 개인정보가 남았는지는 탐지기로 검사하고, **라벨 이름만 기록**합니다.
- **진행**: 117문항 중 19문항 완료
  - LLM API 호출 한도(429) 때문에 문항당 7~50초가 걸립니다.
- **중간 관찰**
  - 마케팅 팀장 Q1·Q2: 대상 문서를 찾았고, 다른 팀 문서는 나오지 않았습니다.
  - 연결 오류 1건 (마케팅 과장 Q2): 끝난 뒤 다시 실행합니다.
  - 원문 의심 1건 (마케팅 과장 Q6 이메일 질문): 탐지기가 답변에서 이름·이메일 원문을 의심했습니다.
    - 근거 문서는 고객편지입니다. **오탐인지 실제 노출인지는 확인 전**입니다.
- 완료되면 `06_테스트_결과.xlsx`에 기록표·판정 집계·문제 목록을 정리합니다.

## 4. 발견한 문제

| # | 문제 | 영향 | 제안 |
|---|---|---|---|
| 1 | 실명 복원 기능 없음, 라벨별 권한 설정 없음 | 요청 정책 ① 전체 미지원 | `개선안_라벨별_실명복원.md` (백엔드) |

| 3 | **탐지 누락 16건**: H0004 H0009 H0011 H0028 H0076 H0079 H0080 H0081 H0123 H0126 H0131 H0135 H0152 H0177 H0182 H0184 | 권한과 관계없이 원문 노출 가능 | 탐지 규칙·모델 보완 후 다시 적재 (가장 시급) |
| 4 | 질문 속 이름표가 탐지되지 않음 | 이름표로 "같은 고객 다른 기록" 검색 불가 | 질문 가명처리 때 이미 있는 이름표를 인식하도록 보완 |
| 5 | 담당자 칸을 중요도 대용으로 사용 | 실제 업무 담당자와 다름 (시나리오 전용) | `docs/document_owner_plan.md`의 근거 있는 담당 결정으로 대체 |
| 6 | LLM API 호출 한도 | 테스트 속도 저하 | 테스트는 시간 간격을 두고 실행 |
