# 개선안: 직급별·라벨별 실명 복원

작성일: 2026-11-24 · 관련: 결과물 2 (개인정보 권한표), 7단계 로드맵 6단계 "출력 재검사와 실명 복원"
상태: **설계 제안 (코드 변경 없음)**

## 1. 지금 흐름과 빠진 곳

```
질문 ─▶ 가명처리 ─▶ 권한 있는 문서만 검색 ─▶ LLM 답변(이름표 그대로) ─▶ 화면
                     allowed_documents()        answer()                server.py /api/chat
                                                                         ▲
                                                       여기에 "재검사 → 복원" 단계가 없음
```

- `server.py`의 `/api/chat`이 `answer()` 결과를 **그대로** 화면에 보냅니다. 87~93번째 줄입니다.
- 원문은 `vault.token_map`(토큰, 라벨, 원문 목록)에만 있습니다. 검색용 계정(`rag_user`)은 vault를 읽을 수 없습니다.
- 정책은 `auth.team_position_policy.can_restore`(켜짐/꺼짐) 하나뿐입니다.

## 2. 고치는 곳 5가지

### ① 정책: "켜짐/꺼짐"을 "라벨 목록"으로 바꾸기 (DB)

`team_position_policy`에 칸 하나를 추가합니다.

```sql
-- 마이그레이션 0005 (예시)
ALTER TABLE auth.team_position_policy
  ADD COLUMN restore_labels text[] NOT NULL DEFAULT '{}'
  CHECK (restore_labels <@ ARRAY['PERSON','PHONE','EMAIL','ADDRESS','RRN','ACCOUNT','CARD']);
```

| 직책 | restore_labels |
|---|---|
| 팀장 | `{PERSON,PHONE,EMAIL,ADDRESS,RRN,ACCOUNT,CARD}` |
| 과장 | `{PERSON,PHONE,ACCOUNT}` |
| 사원 | `{PERSON}` |

- 기존 `can_restore`는 "목록이 비어 있지 않음"과 같은 뜻으로 남겨 두면, 기존 화면과 테스트가 깨지지 않습니다.
- 검색 범위가 `NONE`이면 목록도 비워야 한다는 기존 규칙을 그대로 적용합니다.
- 마이그레이션은 서버를 켤 때 자동으로 적용됩니다 (0003·0004와 같은 방식).

### ② 복원 전용 DB 계정 (DB)

- 새 계정 `restore_user`를 만들고 **`vault.token_map` 읽기만** 허용합니다 (쓰기·삭제 불가).
- 이렇게 하면 검색 코드는 여전히 vault에 접근하지 못하고, **복원 모듈 한 곳만** 원문을 읽습니다. CLAUDE.md의 "vault는 검색·화면 코드에서 직접 다루지 않는다" 원칙을 지킬 수 있습니다.
- 접속 비밀번호는 `.env`에 새 항목으로 넣어야 합니다 (사용자가 직접 입력).

### ③ 복원 모듈 `starter/restore.py` (백엔드)

```python
def restore(text, allowed_labels, allowed_tokens):
    """이름표 중 (허용 라벨) 이면서 (권한 있는 문서에 실제로 나온 토큰) 만 원문으로 바꾼다."""
```

반드시 지켜야 할 조건 세 가지:

1. **라벨 검사**: 토큰 라벨이 내 `restore_labels`에 있을 때만 바꿉니다.
2. **출처 검사**: 그 토큰이 **내가 볼 수 있는 문서**(`allowed_documents`)의 `rag.chunks.tokens`에 있을 때만 바꿉니다.
   - 사용자가 다른 팀 고객의 이름표를 질문에 붙여 넣어도 원문이 나오지 않게 하는 장치입니다.
3. **LLM에는 계속 이름표만** 보냅니다. 복원은 답변이 완성된 **뒤에**, 화면으로 보내기 직전에 합니다.

### ④ 출력 재검사 (백엔드)

복원하기 **전에** 답변을 탐지기에 한 번 더 통과시킵니다.

- 탐지 누락 문서에서 원문 이름이 섞여 들어온 경우, 권한과 상관없이 가립니다.
- 순서: `answer()` → **재검사(원문 PII 가리기)** → **restore()** → 화면

### ⑤ 복원 기록 (DB + 백엔드)

`auth.restore_log`에 누가, 언제, 어떤 문서에서, 어떤 라벨을 몇 개 복원했는지 남깁니다.

- **원문은 기록하지 않습니다.** 토큰과 라벨만 기록합니다.
- 기존 `permission_change_log`와 같은 방식입니다.

## 3. 화면 (프론트, 현호)

| 위치 | 변경 |
|---|---|
| 관리자 → 정책 화면 | 팀·직책마다 **라벨 7개 체크박스**. 저장할 때 사유를 받고 이력을 남김 (기존 저장 흐름 재사용) |
| 챗봇 답변 | 복원된 값은 **다른 색 + 🔓 표시**, 가려진 값은 지금처럼 주황 이름표 → 테스트할 때 한눈에 구분 |
| 챗봇 상단 | "내 열람 권한: 이름·전화·계좌" 표시 (`/me` 응답에 `restore_labels` 추가) |

## 4. 하면 안 되는 방법

- ❌ **브라우저에서 복원하기**: 원문을 화면 코드로 보내는 순간, 권한 없는 라벨도 개발자 도구로 볼 수 있습니다. 복원은 반드시 서버에서 합니다.
- ❌ **LLM에 원문을 주고 답하게 하기**: 외부 API로 개인정보가 나갑니다. 프로젝트의 핵심 원칙(가명처리)과 맞지 않습니다.
- ❌ **`vault_user`(쓰기 가능 계정)를 재사용하기**: 복원 코드에 문제가 생기면 매핑이 바뀔 수 있습니다. 읽기 전용 계정을 따로 둡니다.

## 5. 역할과 순서

| 순서 | 할 일 | 담당 | 끝난 기준 |
|---|---|---|---|
| 1 | 팀 합의: 라벨 목록 방식 채택, 복원 위치(서버), 읽기 전용 계정 | 팀 전체 | 회의록 1줄 |
| 2 | 마이그레이션 0005 (①), `restore_user` 계정 (②) | 백엔드 | 정책에 라벨 목록 저장 가능 |
| 3 | `restore.py` (③) + 재검사 (④) + 기록 (⑤), `/api/chat`에 연결 | 백엔드 | 단위 테스트: 과장 계정에서 이메일은 이름표로, 전화는 원문으로 |
| 4 | 정책 체크박스, 답변 🔓 표시, 내 권한 표시 | 프론트(현호) | 관리자 화면에서 바꾸면 챗봇 결과가 바뀜 |
| 5 | 결과물 2의 21칸 판정 다시 실행 | 현호 + 팀원 | "미지원" 0칸 |

- 3단계 테스트에서 가장 중요한 경우: **다른 팀 고객 이름표를 질문에 붙여 넣었을 때 원문이 나오지 않는지** (출처 검사).
