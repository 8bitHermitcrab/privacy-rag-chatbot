# 종합 프로젝트

## 설치·실행 방법은 [SETUP.md](SETUP.md)를 보세요.

## 로컬에서 쉽게 시작하기

Windows에서는 프로젝트 루트의 **`시스템_시작.cmd`를 더블클릭**합니다.
Docker와 DB 준비 → DB 버전 확인 → 서버 관리자 실행 → 브라우저 열기까지 진행합니다.
이미 켜진 DB와 관리자는 재사용하고 기존 데이터·비밀번호를 초기화하지 않습니다.
관리자 화면에서 챗봇 두 개와 분산기를 시작한 뒤 `http://127.0.0.1:8080`으로 사용합니다.

처음 설치할 때는 Docker Desktop, 프로젝트 `.venv`, `requirements.txt`, 실제 값을 입력한 `.env`가 먼저 필요합니다.
팀 공통 Python 버전은 3.12입니다 (`.python-version`). 탐지기는 macOS, DB·관리자 기능은 Windows에서 3.12 기준으로 확인합니다. 설치 방법은 SETUP.md를 따르세요.
`.env.example`의 예시 비밀번호·키는 실제 사용 설정이 아닙니다. 실제 값은 각 PC의 `.env`에만 입력하세요.
`app.py`의 기존 Streamlit 데모는 선택 기능입니다. 현재 기본 실행은 FastAPI이며 Streamlit 사용 시 별도 설치가 필요합니다.
Docker Desktop이 꺼져 있으면 자동 실행 후 준비를 기다립니다. 최초 이미지 다운로드는 시간이 걸릴 수 있습니다.
최초 관리자 계정이 없으면 임의 비밀번호를 Git 외부의 로컬 파일로 생성하고 파일 위치를 표시합니다.
기동 준비에서 DB 전용 계정과 빠진 필수 구조를 자동 보충한 뒤 버전별 변경을 적용합니다. 자료형 충돌이나 기존 데이터 제약 위반처럼 자동 판단할 수 없는 차이는 상세 항목을 표시하고 해당 단계의 변경을 롤백합니다.
새로 만든 DB에는 테이블만 준비되며 업무 문서·사용자 데이터는 별도 등록입니다.

현재 커밋은 Windows 로컬 운영 기준입니다. Ubuntu 원격 제어·배포 예제는 Git 밖에 별도 백업했으며 클라우드 이전 시 다시 통합합니다.


## 로컬 관리자 사용법

`시스템_시작.cmd`를 더블클릭합니다. Docker·DB 확인과 DB 버전 적용 후 관리자 화면을 엽니다.
이미 켜진 DB와 관리자는 재사용합니다. 기존 데이터·비밀번호는 초기화하지 않습니다.
관리자는 `http://127.0.0.1:9000`, 분산기를 통한 챗봇은 `http://127.0.0.1:8080`입니다.
관리자에서 챗봇 서버 1·2와 분산기를 시작합니다. 등록 인스턴스의 로컬 포트는 8001·8002입니다.
현재 분산기는 한 PC의 개발용 구성으로, PC 자체 장애를 견디는 운영용 이중화가 아닙니다.

### 계정·비밀 설정

비밀 설정은 Windows `%LOCALAPPDATA%\RagServerAdmin`에 저장하며 Git에 넣지 않습니다.
최초 관리자 로그인 정보는 이 폴더의 `initial-login.txt`에 있습니다. 비밀번호 변경 시 초기 파일은 삭제됩니다.
시스템 기동 준비와 모니터링 계정 설치에는 `.env`의 DB 관리자 계정을 사용합니다. 준비 후 스키마 변경은 migration_user, 검색·매핑·업무 관리 서비스는 각 전용 계정을 사용합니다.
로그인 실패 5회 시 15분 제한, 미사용 30분 또는 최대 8시간 경과 시 세션이 만료됩니다.
관리자는 로컬 주소에서만 실행하며 외부 공개·임의 명령 실행을 지원하지 않습니다.
비밀번호를 잊으면 관리자 프로그램을 중지하고 아래 명령을 실행한 뒤 다시 시작합니다.

```powershell
python -m server_admin --setup --generate --reset
```

### 서비스 제어

챗봇 시작·중지·재시작, 트래픽 제외·복귀·가중치 변경을 지원합니다.
중지·재시작은 새 요청 제외 → 처리 중 요청 대기 → 중지 → 기동 확인 → 필요 시 복귀 순서입니다.
기본 대기 시간은 120초이며 화면에서 15~120초로 저장합니다. 초과하면 강제 종료하지 않고 보류합니다.
다른 정상 서버가 없으면 마지막 서버를 제외하거나 중지하지 않습니다.
처리 중 요청 수는 분산기를 거친 요청 기준입니다. 직접 인스턴스로 접속한 요청은 포함하지 않습니다.
개발용 분산기는 GET/HEAD만 연결 오류 시 우회 재시도하고, POST는 중복 실행을 막기 위해 재시도하지 않습니다.
분산기 자체 중지·재시작은 전체 접속이 잠시 끊길 수 있습니다. 기록은 관리자 프로그램의 작업만 포함합니다.

### DB 버전 관리

`시스템_시작.cmd`의 3/5 단계에서 아래 두 작업을 순서대로 실행합니다.

1. DB 전용 계정·pgvector·누락된 필수 구조 준비 (`--prepare`).
2. 미적용 Alembic 버전 변경 실행 (현재 `0002`).

| DB 상태 | 실행 결과 |
|---|---|
| 완전히 빈 DB | 필요한 계정·테이블·제약·인덱스·갱신 함수를 생성하고 최신 버전까지 적용 |
| 기존 스타터 DB | 청크·토큰을 보존하며 빠진 필수 구조를 추가하고 버전 등록 |
| 버전 등록된 DB, 변경 없음 | 구조·접속 설정을 확인하고 기존 데이터·비밀번호 유지 |
| 새 변경 버전 있음 | 이전 버전 이후의 `upgrade()`만 실행 |
| 기존 열 순서·제약 이름이 다르지만 의미가 같음 | 기존 구조를 유지하고 호환성 확인 |
| 자료형·자동번호 의미 충돌, NULL·중복·참조 오류 | 대상 테이블·열·제약을 표시하고 해당 준비/변경 트랜잭션 전체 롤백 |

정식 업무 테이블은 10개이며 `public.alembic_version`은 별도의 버전 관리용 테이블입니다.
기존 청크에 대응하는 문서 메타데이터가 없으면 문서 ID와 유형만 `PENDING`으로 보충합니다.
담당 직원·팀·권한을 추측하거나 문서를 자동 확정하지 않습니다. 기존 청크·토큰·인물·계정은 삭제하지 않습니다.
추가 열과 별도 테이블도 유지합니다. 임베딩 차원 변경, 주민번호·전화번호 값 변환, scalar↔배열 변환은 자동으로 하지 않습니다.

`.env`에는 실제 DB 관리자 접속 정보와 `RAG_PASSWORD`, `VAULT_PASSWORD`, `MIGRATION_PASSWORD`가 필요합니다.
없는 서비스 계정은 설정값으로 생성하고, 이미 있는 계정은 비밀번호 일치 여부부터 확인합니다.
기존 계정의 비밀번호를 `.env` 값으로 임의 초기화하지 않습니다.
`DB_PORT`는 해당 PC의 실제 포트를 사용하며 Docker의 공개 포트도 이 값을 따릅니다. 5432/5433을 고정 가정하지 않습니다.

```powershell
# 프로젝트 루트에서 수동 점검/설치 준비가 필요한 경우
& ".\.venv\Scripts\python.exe" -B -m starter.migrate --check
& ".\.venv\Scripts\python.exe" -B -m starter.migrate --prepare
& ".\.venv\Scripts\python.exe" -B -m starter.migrate

# 다음 버전 작성: 생성 파일의 upgrade()를 구현한 뒤 배포
& ".\.venv\Scripts\python.exe" -B -m starter.migrate --new "변경 설명"
```

`--check`는 구조/버전을 읽기만 하며 계정·테이블을 만들지 않습니다.
이미 배포한 버전 파일은 수정하지 않고 새 리비전을 추가합니다.
시작 실패 시 정리된 상세 원인을 CMD에도 표시하며 비밀번호·API 키·원문 행 값은 출력하지 않습니다.

#### DB 설치 경로 검증

```powershell
# 운영 볼륨을 연결하지 않는 별도 임시 PostgreSQL 컨테이너에서 검증
& ".\.venv\Scripts\python.exe" -B tools/verify_schema_install.py

# 업무·서버 관리자 회귀 검증
```

격리 검증은 계정이 전혀 없는 새 서버, 기존 스타터 데이터, 추가 열/PK 이름 차이, 반복 기동,
동시 설치, 버전 정보 누락, 빠진 열 보충, 자동번호, 잘못된 비밀번호, 자료형·중복 데이터 충돌 시 롤백을 확인합니다.
검증 전용 컨테이너만 종료하고 제거하며 운영 DB를 삭제/초기화하지 않습니다.

### 실행 구조·검증

`server_admin/__main__.py`는 실행, `security.py`는 인증·비밀 설정, `operations.py`는 제어·상태, `app.py`는 API, `proxy.py`는 로컬 분산기입니다.
HTML·CSS·JavaScript는 `server_admin/web/`, 회귀 테스트는 `server_admin/test_admin.py`에 모았습니다.

```powershell
python -m unittest server_admin.test_admin -v
python -m server_admin --start --no-browser
```

직접 관리자만 실행하려면 `python -m server_admin`을 사용합니다.


## 기존 UI 기반 업무 관리자 DB 연결

업무 관리자: `http://127.0.0.1:8080/admin` / 로그인: `/login`
서버 관리자: `http://127.0.0.1:9000` (별도 프로그램·계정)

`web/admin.html`의 원래 CSS·사이드 메뉴·대시보드·화면 템플릿 6개를 유지합니다.
연동 코드는 `web/business_admin.js`, 인증·업무 DB API는 `starter/business_admin.py`에 있습니다.
기존 HTML에 들어 있던 예시 회원·직원·탐지 후보·활동 기록은 불러오거나 DB에 적재하지 않습니다.

| 원래 화면 | 실제로 연결한 기능 | 연결 보류 |
|---|---|---|
| 대시보드 | 실제 계정 수·활성 수·역할 비율·최근 계정·최근 DB 이력 | 가입 승인 대기·검색 요청 통계·보안 경고 집계 |
| 회원 목록 | 실제 계정 조회·검색·필터·상세·정지/해제·새로고침, 회원 초대 (사번만 입력 → 아이디=사번·STAFF 계정 발급, 없는 사번은 '확인 전' 직원으로 등록, `POST /api/admin/invite`) | 가입 승인·인사 명부 대조 |
| 권한 탭 | 역할 변경 저장·팀/직책 정책에 따른 검색 범위 조회·CSV | 개인별 검색/복원 예외·회원 화면에서 직원 소속 팀 변경 |
| 팀 관리 | 실제 팀/직원 조회·계정 연결·팀 기본 정보 생성·직책별 검색 정책 일괄 편집·CSV | 직원 등록/수정 화면·계정 연결 해제 처리 |
| 활동기록 | 기존 permission_change_log의 최근 100건 조회·검색·기간 필터·CSV | 실명 복원 전용 감사 기록 |
| 탐지 검토 | 기존 화면 유지·연결 보류 표시 | 원문 보기·후보 수집·수정 저장·재가명처리/재색인 |
| 시스템 환경 | 실제 API 응답·업무 DB 연결·모델 설정 조회 | LLM 호출 점검·탐지 품질·백업/저장소·오류 집계 |

보류 기능은 DB 저장 요청을 보내지 않습니다. 조회할 근거가 없는 통계는 0이나 정상으로 꾸미지 않고
미연결/미집계/확인 안 됨으로 표시합니다. 이름·이메일은 DB에 해당 표시 필드가 없어 `—`로 둡니다.

직원은 `auth.employee_info.employee_id`(사번), `team_id`, `position_code`로 관리합니다.
이름 토큰 입력·vault 이름 토큰 대조는 제거했습니다. 과거 `name_token` 열은 데이터 보존을 위해 남겨두지만
새 직원 저장 API·화면·권한 계산에서는 사용하지 않습니다. 직원 확정에는 소속 팀과 직책이 필요합니다.

### 검색 정책과 DB 버전 0002

`auth.team_position_policy` 한 테이블을 추가했습니다. 기본키는 `(team_id,position_code)`이고,
팀 외래키, `search_scope`(OWN/TEAM/NONE), `can_restore`, 생성/수정 일시를 저장합니다.
직원의 소속 팀과 직책이 모두 일치하는 정책만 적용하며, 없으면 검색을 차단합니다.
계정 관리 권한은 기존 역할의 `can_manage_users`로 따로 판단합니다.
기존 role_info의 검색·복원 열은 보존하지만 새 권한 계산에서는 사용하지 않습니다.
`can_restore`는 현재 정책 값만 저장하며 실제 실명 복원 기능은 제공하지 않습니다.

기존 UI의 팀 목록 → **권한 설정** 또는 팀 상세 → **이 팀 권한 설정**에서
같은 사이드 패널 안의 직책별 행으로 검색 범위를 설정합니다.

- 팀장·과장·사원과 기존 정책/소속 직원에 있는 직책을 표시합니다. 미설정 행의 기본값은 검색 불가입니다.
- 직책별로 소속 팀 전체 문서(TEAM), 본인 담당 문서(OWN), 검색 불가(NONE)를 고릅니다.
- 직책 추가로 다른 직책을 등록할 수 있습니다. 저장된 직책 이름은 고정이며 검색 불가로 비활성화합니다.
- 변경 사유 입력 후 직책별 권한 저장을 누르면 변경한 행을 한 트랜잭션으로 저장하고 이력을 남깁니다.
- 다른 관리자가 같은 행을 변경했으면 어느 행도 저장하지 않고 다시 확인하도록 안내합니다.
- 같은 팀·직책 직원의 다음 검색 요청부터 적용합니다. 직원 확정·팀 활성·문서 확정 조건도 필요합니다.
- 복원 종류와 금융 문서 구분은 이번 편집에서 다루지 않습니다. 기존 복원 설정은 보존하되 NONE으로
  변경할 때는 DB 정책에 맞춰 복원 허용도 끕니다. 실제 실명 복원 기능은 미연결입니다.

추가 DB 테이블이나 제약조건 없이 기존 `auth.team_position_policy`를 사용합니다.
일괄 저장 API는 `POST /api/admin/policies/batch`이며 계정 관리 권한·Origin·CSRF와 행 버전을 검사합니다.

프로그램 시작 시 Alembic이 `0001 → 0002`를 적용합니다. 최초 구조/검증 파일은 수정하지 않고
새 리비전과 `migrations/0002_contract.json`으로 변경된 구조를 검사합니다.
0002는 직원 확정에 이름 토큰을 요구하던 CHECK를 소속 팀 확인으로 바꾸고, 정책 테이블만 추가합니다.
기존 계정·팀·문서·토큰·인물 데이터와 관리자 비밀번호는 초기화하지 않습니다.
기본 역할이 없는 새 DB에만 필요한 역할 3개를 준비하며 기존 역할 설정을 덮어쓰지 않습니다.

챗봇의 HTTP API는 로그인·직원 확정·팀 활성·정책을 검사하고, 확정된 담당 문서/팀 문서만 SQL 후보로 선택합니다.
직접 실행하는 검색 CLI/DB 접속은 별도의 유지보수 경로입니다. 문서 권한을 자동 확정하지 않습니다.
원래 관리자 UI에 문서 담당자 확정 메뉴가 없으므로 해당 화면도 임의 추가하지 않았습니다.

### 로그인과 실행

`시스템_시작.cmd`로 DB 마이그레이션과 업무 접속 계정을 준비합니다.
웹 프로그램은 `auth_user`로 업무 정보를 관리하고 DB `admin`으로 접속하지 않습니다.
`auth_user`는 auth 업무 테이블의 조회/등록/수정, 이력 조회/추가, rag.document_info 조회/수정만 허용하며
rag.chunks 및 vault 원문을 직접 조회할 권한은 없습니다.
빈 계정 DB에만 최초 `businessadmin`을 생성합니다. 초기 로그인 정보와 접속 비밀 설정은 Git 밖의 보호 폴더에 저장합니다.
Windows: `%LOCALAPPDATA%/RagServerAdmin`, 우분투: `~/.local/share/rag-server-admin`.
`business-initial-login.txt`는 최초 발급 정보이며 이후 변경·복구한 비밀번호를 의미하지 않습니다.
로그인 후 초기 비밀번호를 변경하고 초기 발급 정보 파일은 전달 후 삭제하세요.

비밀번호는 PBKDF2-SHA256으로 저장하며 개인정보 가명처리 HMAC 키와 공유하지 않습니다.
서명 쿠키와 DB 계정 버전으로 두 노드의 세션을 확인하며 로그인은 30분 후 만료됩니다.
계정 수정·비밀번호 변경·로그아웃은 기존 세션을 만료시킵니다. 로그아웃은 해당 계정 전체 세션에 적용됩니다.
로그인 실패는 마지막 비밀번호 변경 이후 5회/15분으로 제한합니다. API 쓰기는 Origin·CSRF를 검사합니다.
변경 버전이 다르면 저장을 거절하고 본인 관리 권한 해제와 마지막 관리자 해제를 막습니다.

클라우드 공개 전 HTTPS를 구성하고 `BUSINESS_ALLOWED_ORIGINS=https://업무서비스주소`,
`BUSINESS_COOKIE_SECURE=1`을 설정하세요. 기본 허용 Origin은 localhost/127.0.0.1의 8000/8001/8002/8080입니다.
노드를 물리적으로 분리하면 업무 접속 설정과 서명 키도 안전하게 동일하게 배포해야 합니다.

검증: `python -B -m unittest starter.test_business_admin server_admin.test_admin -q`.
검증용 계정·직원·팀·정책은 롤백하며 남기지 않습니다. PostgreSQL identity 번호 소비는 롤백되지 않으므로 간격은 생길 수 있습니다.
