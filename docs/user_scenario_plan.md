# 권한별 사용자 시나리오 검증 계획서

작성일: 2026-11-24 · 작성: 프론트엔드(현호) · 성격: **코드 개발 없음, 기존 시스템으로 확인하는 테스트 계획**

## 0. 한 줄 요약

기존 187개 문서와 이미 등록된 직원을 그대로 쓰고, **마케팅팀·인사팀·개발팀의 팀장·과장·사원 9명에게 로그인 계정만 발급**합니다.
그다음 같은 질문을 9개 계정으로 던져서 **검색되는 문서와 보이는 개인정보가 어떻게 달라지는지** 기록합니다.
요청서의 권한 중 **지금 시스템이 지원하지 않는 것**은 "지원됨"이라고 가정하지 않고, 결과표에 **"미지원"**으로 따로 표시합니다.

## 2. 작업 원칙 (요청서 9장 반영)

1. **코드 수정 없음.** 관리자 화면에 이미 있는 기능(계정 발급, 정책 저장)만 씁니다.
2. **문서 원문, 담당 팀·직원은 바꾸지 않습니다.**
3. **DB를 바꾸는 작업은 5장 목록을 보여 드리고 승인받은 뒤에만** 진행합니다. 모든 변경은 사유와 함께 이력(`permission_change_log`)에 남습니다.
4. **개인정보는 이름표(`<PERSON_…>`)와 문서 번호(H0001…)로만** 다룹니다. 원문을 파일·답변에 옮기지 않습니다.
5. **결과물의 모든 표에 `[가상]`과 `[실제]`를 구분해 적습니다.** 예: "중요도 = [가상] 분류안", "검색 결과 = [실제] 챗봇 출력"

### 단계 4. 중요도 분류 기준 (초안)

문서 유형만 보지 않고, **가명처리된 본문에 어떤 개인정보 이름표가 있는지**도 함께 봅니다.

| 등급 | 기준 (둘 중 더 높은 쪽) | 접근 가능 직급 [가상 정책] |
|---|---|---|
| 일반 | 공지·안내·내부 업무 기록, 고객 개인정보 없음 | 팀장·과장·사원 |
| 중요 | 고객 상담·처리 기록, 또는 이름·전화번호·계좌번호가 있음 | 팀장·과장 |
| 매우 중요 | 심사·사고·민원 기록, 또는 주민등록번호·카드번호·주소·이메일이 있음 | 팀장 |
| **검토 대상** | 유형과 개인정보 기준이 서로 다르거나, 탐지 누락이 의심되는 문서(예: 이름이 가명처리되지 않은 문서) | 확정하지 않음 |

- 분류표 열: 문서 번호 · 유형 · 담당 팀 · [실제] 담당 직원 · 포함 라벨(종류별 개수) · [가상] 등급 · [가상] 접근 직급 · [실제] 지금 접근 가능한 직급 · 판단 근거 · 검토 필요
- "[실제] 지금 접근 가능한 직급" 칸으로 **정책과 현실의 차이**가 바로 보이게 합니다.

### 단계 5. 시나리오와 질문 설계

- **기준 고객**: 각 팀 문서에 나오는 고객 이름표 1~2개를 고릅니다. 여러 등급의 문서에 함께 나오는 고객을 우선합니다.
  - 질문은 이름표로 합니다. 예: "`<PERSON_…>` 고객의 상담 기록을 찾아줘"
  - 실명을 몰라도 같은 문서를 찾을 수 있고, 원문을 다루지 않아도 됩니다.
- **질문 세트 (계정마다 같은 질문, 약 10개)**

| # | 질문 유형 | 보는 것 |
|---|---|---|
| Q1~Q3 | 우리 팀 일반·중요·매우 중요 문서 검색 | ② 직급별 문서 |
| Q4~Q7 | 기준 고객의 상담 기록 / 전화번호 / 계좌번호 / 주소·이메일·주민번호·카드번호 | ① 개인정보 라벨 |
| Q8~Q9 | 다른 두 팀의 대표 문서 내용 질문 | ③ 팀 차단 |
| Q10 | 다른 팀 고객 이름표로 질문 | ③·④ 정보 새어 나감 |

- 9개 계정 × 10문항 = **90건**을 기록합니다.

### 단계 7. 실행 방법과 기록 항목

- **실행**: 계정마다 시크릿 창에서 `http://127.0.0.1:8080/login`으로 로그인합니다. 근거 문서 번호는 답변 아래 **"🐾 어흥이가 찾은 자료 보기"**에서 확인합니다. 끝나면 로그아웃합니다.
- 반복 실행이 필요하면, 예전에 만든 확인 스크립트(로그인 → 질문 → 근거 문서 수집)를 임시 폴더에서 재사용합니다. 프로젝트 코드는 바꾸지 않습니다.
- **기록표 열** (요청서 6장): 로그인 계정(팀·직급) · 질문 · 기대 결과 [가상 정책 기준] · 실제 결과(근거 문서 번호, 답변 요약) · 개인정보 노출(표시된 라벨, 원문 노출 여부) · 통과/실패/**미지원** · 비고(원인)
- **판정 규칙**
  - 통과: 기대와 실제가 같음
  - 실패: 권한 밖 문서가 나왔거나, 원문 개인정보가 보이거나, 권한 안의 문서가 안 나옴
  - 미지원: 기대 결과가 지금 없는 기능(라벨별 복원, 중요도 차단)에 달려 있음. 이것은 실패와 따로 셉니다.
