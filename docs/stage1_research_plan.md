# 실전 프로젝트 1

## 1. Background & Baseline

### 1-1. 기존 연구의 접근

| 접근 | 대표 사례 | 어떻게 풀었나 | 우리에게 주는 시사점 |
| --- | --- | --- | --- |
| **규칙 + 기계학습 하이브리드** | 2014 i2b2 의료 기록 비식별화 챌린지 (CRF + 규칙 하이브리드, Yang & Garibaldi, 2015) | 통계 모델(CRF)과 정규식·키워드 규칙을 함께 쓰고 결과를 규칙으로 합침. 챌린지 1위도 하이브리드 | 한 방식보다 방식을 섞는 쪽이 강함 |
| **실무 도구 (정규식 + NER)** | Microsoft Presidio | 카드번호·이메일 같은 정형 개체는 정규식과 체크섬, 이름·장소·기관은 NER 모델로 탐지. 기본은 영어만 지원 | 라벨 종류별로 다른 탐지기를 쓰는 구조, 한국어는 직접 맞춰야 함 |
| **한국어 개체명 인식(NER)** | KLUE-NER, 한국어 개인정보 NER (Applied Sciences, 2024) | 글자 단위 BIO 태깅으로 사람·기관 등을 탐지. 개인정보 태그 33종으로 BERT·ELECTRA를 미세조정한 연구도 있음 | 토큰 분류 방식의 근거. 모델마다 라벨 체계가 달라 우리 라벨 8종과 맞춰야 함 |
| **LLM 기반 탐지** | 다국어 하이브리드 PII 탐지 평가 (arXiv 2510.07551), PII 탐지기 강건성 연구 (arXiv 2609.03464) | 프롬프트만으로(zero-shot) 탐지. 한 연구에서는 하이브리드보다 낮았고 출력 형식이 들쭉날쭉함. 다른 연구에서는 전체 점수는 높지만 처음 보는 데이터에서 가장 크게 떨어짐 | LLM은 일관성과 holdout 하락을 반드시 측정해야 함 |
| **한국어 형태소 분석** | Kiwi (이민철, 2024) | 통계 언어 모델 + Skip-Bigram으로 형태소 분석의 모호성을 해소하고 빠름 | 조사 분리(`윤선영은` → `윤선영`  • `은`)에 사용 |

위 자료는 초록·요약 수준에서 확인했습니다. 서로 다른 평가 기준의 점수라 숫자를 직접 비교하지 않습니다.

### 1-2. Baseline

- **Baseline: 강사 제공 토큰 분류(BIOES) 기준 모델 단독**. 후처리·규칙 없이 그대로 쓴 결과를 기준선으로 둡니다.
- 비교 대상: 추가 토큰 분류 모델 1개 이상 (후보: Hugging Face koelectra-ko-pii-ner, 라이선스 확인 후 확정), 규칙 기반 탐지기, 클라우드 LLM

## 2. Proposed Method

### 2-1. Problem Definition

- **Task**: Information Extraction — 개체명 인식(NER) 형태의 **개인정보 구간(span) 탐지**. 문서를 넣으면 (시작 위치, 끝 위치, 라벨) 목록을 돌려줌
- **라벨 8종**: `person`, `phone_number`, `organization`, `email`, `address`, `resident_registration_number`, `account_number`, `card_number`
- **해결할 문제**: 한국어는 같은 개인정보가 조사(`윤선영은`), 띄어쓰기(`윤 선영`), 번호 형식 변형(하이픈 없는 전화번호)으로 나타나고, 대표번호·상품명 같은 오탐 미끼도 있어 한 가지 방식으로는 놓치는 개인정보가 생김
- **왜 중요한가**: 금융사가 상담 기록·민원·메일을 LLM·RAG에 쓰려면 개인정보를 먼저 찾아야 함. 탐지에서 놓친 값은 벡터 DB·LLM 로그·외부 API로 그대로 흘러가므로, 탐지는 이후 가명처리 챗봇(실전 2·종합) 전체의 안전을 결정하는 첫 단계임. 하나 더 가리는 것보다 하나 놓치는 비용이 훨씬 큼

### 2-2. 적용할 아이디어

**한국어 특성을 반영한 라벨별 하이브리드 탐지기**

1. **한국어 규칙 탐지기**: 번호류 5종 정규식(하이픈·공백 변형 포함) + Kiwi로 조사를 분리한 뒤 성씨 목록·호칭 규칙(씨, 님, 고객, 과장 등)으로 이름 후보 탐지
2. **경계 보정 후처리**: 모델·LLM이 잡은 구간 끝에 붙은 조사를 떼어 내 경계 오류를 줄임
3. **합집합(union)**: baseline 결과에 정규식 결과를 합쳐 미탐을 줄임
4. **라벨별 라우팅**: dev에서 라벨마다 재현율이 가장 높은 방식을 골라 쓰는 조합 (예: 번호류는 규칙, 이름·주소·기관명은 모델)

### 2-3. Baseline 대비 무엇이 다른가

| 항목 | Baseline | 제안 방식 |
| --- | --- | --- |
| 탐지기 | 토큰 분류 모델 1개 | 라벨별로 규칙·모델 중 더 나은 쪽을 골라 쓰고, 정규식을 합침 |
| 한국어 처리 | 없음 (모델이 학습한 대로) | Kiwi 조사 분리, 호칭 규칙, 경계 보정 |
| 번호 형식 변형 | 학습 데이터에 없던 형식은 놓칠 수 있음 | 하이픈·공백 변형을 정규식으로 처리 |
| 우선 목표 | 전체 F1 | 재현율·마스킹 재현율 (정밀도는 하한선만 지킴) |

### 2-4. Dataset & Preprocessing

**사용할 데이터셋**: 금융사 개인정보 가상 데이터셋 `pii_synth_finance` (강사 제공)

| 세트 | 건수 | 용도 |
| --- | --- | --- |
| dev | 100 | 규칙 작성·개선·오류 분석 |
| test | 200 | 중간 확인 (결과를 보고 다시 고치지 않음) |
| holdout | 147 | 최종 평가 (새 템플릿 16종·새 인물, 최종 평가 전까지 열지 않음) |

**데이터 특성**

- 가상 카드사 "새봄카드"의 사내 문서, 문서 유형 14종(상담·민원·메일·회의록 등), 개인정보 없는 문서 50건 포함
- 라벨 8종, 개체 1,887개. 사람이 쓴 빈칸 템플릿에 가상 값을 채워 만들어 정답 위치가 정확함
- 어려운 사례 태그: 띄어 쓴 이름, 조사 부착, 동명이인(4쌍), 전화번호 형식 변형, 오탐 미끼
- 주의: 템플릿으로 만들어 dev 점수가 실제보다 좋게 나오기 쉬움 → holdout으로 확인

**전처리 방법**

1. **원문 위치 보존**: 전처리는 탐지용 사본에만 하고, 결과 위치는 항상 원문 기준 글자 위치로 되돌려 채점
2. **형태소 분석**: Kiwi로 조사·어미를 분리하고 고유명사 태그를 얻음 (규칙 탐지기용)
3. **번호 정규화**: 하이픈·공백을 없앤 형태로도 매칭하고, 찾은 위치는 원문으로 환산
4. **모델 출력 정렬**: 토큰 분류 모델의 하위 단어(subword) 예측을 글자 위치로 변환
5. **라벨 대응표**: 추가 모델의 라벨을 우리 8종으로 매핑 (없는 라벨·묶인 라벨 처리 기준 명시)
6. **LLM 출력 변환**: JSON으로 받은 개인정보 문자열을 원문에서 찾아 위치로 변환
7. **팀 라벨 기준**: `김 과장`처럼 라벨 없는 표현의 처리 기준을 1일차에 정하고 일관되게 적용

**쓰지 않는 것**: 이름 사전에 데이터셋 인물 목록(`personas.json`)을 쓰면 정답을 미리 보는 것이므로 일반 성씨 목록만 사용

### 2-5. 왜 효과가 있을 것으로 예상하는가 (가설)

| 가설 | 근거 | 확인 방법 |
| --- | --- | --- |
| **H1**. 번호류 5종은 정규식이 모델보다 재현율이 높고 빠르다 | 모양이 일정한 개체는 실무 도구도 정규식을 씀 (Presidio) | 라벨별 재현율, 문서당 처리 시간 비교 |
| **H2**. 조사 분리·경계 보정으로 경계 오류가 줄어 이름의 정확 일치 재현율이 오른다 | 한국어 이름 뒤에는 조사가 붙어 구간이 길게 잡히기 쉬움 | 경계 오류 건수, `조사 부착` 태그 재현율 비교 |
| **H3**. 합집합은 재현율·마스킹 재현율을 올리고 정밀도는 조금 낮춘다 | 서로 다른 방식은 놓치는 사례가 다름 (i2b2 하이브리드) | baseline vs baseline + 정규식 비교 |
| **H4**. LLM은 처음 보는 표현에 유연하지만 느리고 반복 실행 결과가 달라 단독 운영에는 부적합하다 | LLM은 출력이 들쭉날쭉하고 처음 보는 데이터에서 크게 하락한 사례가 있음 | 3회 반복 일치율, 처리 시간, test→holdout 하락폭 |

## 3. Experiment Design

### 3-1. 실험 목록

| 실험 | 내용 | 확인하는 것 |
| --- | --- | --- |
| E1 | Baseline: 기준 토큰 분류 모델 | 기준선 |
| E2 | 추가 토큰 분류 모델 (Hugging Face 1개 이상) | 모델 카드 점수와 우리 데이터 점수의 차이 |
| E3 | 규칙 기반 (정규식 + Kiwi + 호칭) | H1, H2 |
| E4 | LLM 탐지, 같은 문서 3회 반복 | H4 |
| E5 | Baseline + 정규식 합집합 | H3 |
| E6 | **제안 방식**: 라벨별 라우팅 + 경계 보정 | baseline 대비 개선폭 |

### 3-2. 비교 방법

- 같은 데이터·같은 채점 도구(`run_compare.py`)·같은 CPU 환경에서 E1~E6 비교
- 전체 / 라벨별 / 어려운 사례 태그별로 나눠 비교
- dev → test → holdout 순서로 방식별 순위가 유지되는지, 어느 방식이 가장 많이 떨어지는지 비교
- 오류 유형(정확 일치·경계·라벨·미탐·오탐)별 건수를 방식마다 비교

### 3-3. Evaluation Metrics

| 지표 | 정의 | 역할 |
| --- | --- | --- |
| **재현율 (Recall)** | 정답 개인정보 중 라벨과 위치까지 맞힌 비율 (정확 일치) | 주 지표 |
| **마스킹 재현율 (mask_rec)** | 라벨이 틀려도 개인정보 위치가 가려진 비율 (정확한 계산 방식은 `run_compare.py` 기준) | 주 지표 (운영 안전성) |
| 정밀도 (Precision) | 탐지한 것 중 실제 개인정보의 비율 | 하한선 (너무 많이 가리면 실전 2 검색이 망가짐) |
| F1 | 정밀도와 재현율의 조화 평균 | 참고 |
| 처리 시간 | CPU 기준 문서 1건 처리 시간, 1만 건 환산 | 운영 가능성 |
| 일관성 | 같은 문서를 3번 돌렸을 때 결과가 같은 비율 | LLM 운영 가능성 |

**왜 이 지표인가**: 개인정보 탐지는 놓치는 비용이 훨씬 커서, F1 하나로 순위를 매기면 미탐이 가려집니다. 재현율을 주 지표로, 정밀도는 하한선으로 둡니다.

**통과 기준 (잠정, 3일차 dev 결과 후 확정)**

| 라벨 | 목표 재현율 |
| --- | --- |
| 주민번호 · 카드번호 · 계좌번호 | 99% 이상 |
| 전화번호 · 이메일 | 98% 이상 |
| 이름 | 95% 이상 |
| 주소 · 기관명 | 90% 이상 |
| 전체 정밀도 | 80% 이상 (하한선) |

위 숫자는 공식 기준이 아닌 팀 제안입니다.

**검증 방법**

- 개선은 dev에서만, test는 중간 확인에 한 번, holdout은 최종 평가에만 사용 (holdout 채점 시점은 강사님께 확인)
- dev→test→holdout 점수 차이로 과적합 점검. 특정 문서 문구에 기대는 규칙은 holdout에서 떨어질 것으로 보고 따로 표시
- 오류 CSV에서 방식별 대표 사례를 뽑아 원인 분석
- 운영 관점: 실제 고객 문서라면 원문을 클라우드 LLM에 보낼 수 없으므로 대안(로컬 LLM 등)을 함께 검토
